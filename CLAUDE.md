## API gotchas hit during development (guppylang 1.0.2)

These cost real debugging time. Read before writing a new package.

1. **`state_result` -> `state_output`.** Renamed in the 1.0 line; `guppylang.std.debug.state_result` still exists as a deprecated alias (`state_result = state_output`), but write `state_output`.

2. **`link_name` kwarg removed from `@guppy`.** `@guppy(link_name="...")` now raises `TypeError`. Use the separate `@link_name(...)` decorator from `guppylang.library`, placed *below* `@guppy`/`@guppy.declare`:
   ```python
   from guppylang import guppy
   from guppylang.library import link_name

   @guppy
   @link_name("my_registry.my_func")
   def my_func(...) -> None: ...
   ```

3. **`.compile()`/`.emulator()`/`.compile_function()` default to `OptimizationLevel.Default`, which imports `pytket.passes.RemoveRedundancies`.** On this dev machine, a Windows Application Control policy blocks pytket's compiled extension (`pytket._tket.architecture`, a `.pyd`) outright -- `ImportError: DLL load failed while importing architecture: An Application Control policy has blocked this file`, reproducible on every attempt (not transient). Fix: use `.with_minimal_opt()` (applies zero passes, never imports pytket) or `.with_opt_level(OptimizationLevel.Classical)` (uses the newer Rust `tket` package instead of `pytket`, which is *not* blocked). This whole package's source and tests use `.with_minimal_opt()` throughout for this reason -- also arguably the right default for a small library function, since it keeps the compiled circuit structurally predictable.

   Separately: on this machine, *other* native DLLs/executables (`hugr._hugr`, and the actual Selene runner subprocess spawned by `emulator(...).run()`) are sometimes transiently blocked by the same Application Control policy the *first* time a fresh process touches them, then succeed on an immediate retry -- looks like a scan-on-first-access policy, not a real block. `tests/test_correctness.py`'s `_run_case()` retries subprocess launches up to 3 times for this reason. If you hit `OSError: [WinError 4551] An Application Control policy has blocked this file` or a DLL `ImportError` mentioning "Application Control policy", retry once or twice before assuming something is actually broken.

   Update while building `packages/qaoa`: this can get *much* worse in bursts. `packages/qaoa`'s test suite and `optimize_qaoa` spawn many more Selene subprocesses per run than `packages/qft`/`packages/grover` (a classical optimization loop compiles+runs a fresh circuit per objective evaluation), and during one stretch of this session even a single, low-volume test (one `.run()` call) failed after exhausting 10 retries with escalating backoff (up to 6s between attempts, ~30s+ total) -- then passed cleanly on the very next, unmodified run, twice in a row, in under 40s. This is genuinely bursty and system-wide (not proportional to any one test's call volume in the moment it happens), not something a fixed retry budget inside one Python process can fully absorb. `packages/qaoa/src/qaoa/qaoa.py`'s `run_qaoa` and its test suite's `_run_with_retry` both retry (10 attempts, linearly increasing backoff capped at 6s) as a reasonable default, but if a test still fails with this exact `WinError 4551` message (check the message -- don't assume a QAOA test failure is this without checking, it could be real), just rerun; it is not a sign anything is actually broken. If this becomes a recurring problem, investigate whether something on the machine (real-time AV scanning, in particular) is backlogged from the sheer number of subprocesses this whole registry's test suites spawn across a long session, rather than adding more retries.

4. **Linking a compiled function's `Package` via `libs=[...]` fails unless the module's entrypoint is reset to its root.** `some_func.compile_function()` still marks that specific function as the HUGR module's entrypoint. Linking two modules that both have a non-root entrypoint raises `hugr._hugr.linking.HugrLinkingError: Cannot link two modules with non-root entrypoints together`. Fix, before serializing/linking a library package:
   ```python
   package = my_func.with_minimal_opt().compile_function()
   for module in package.modules:
       module.entrypoint = module.module_root
   ```
   See `packages/qft/examples/build_lib.py` for the full working pattern (build + `Package.to_bytes()`/`from_bytes()` round trip + `@guppy.declare` + `@link_name` + `.emulator(libs=[...])`), validated end-to-end across two separate Python processes.

5. **`iqft` run in isolation (no call to `qft` anywhere in the same compiled program) produces a different, wrong unitary than the exact same `iqft` run in a program that also calls `qft`, and this can non-deterministically corrupt other, unrelated compilations in the same process too. Significant, unresolved upstream.**

   Core (deterministic) repro: compile+run a program that only calls `iqft` on X-prepared basis states and reads out `state_output` -- the resulting matrix is unitary but does not match the exact inverse-QFT matrix (`numpy.fft.fft(eye, norm="ortho")`), off by a consistent, non-trivial pattern (extra ~`pi/2**(n+1)`-scale phase structure), reproduced identically across many runs. The *exact same* `iqft` function, in a program that also calls `qft` on the *same register* (either order: `qft` then `iqft`, or `iqft` then `qft`; a throwaway `qft` call on an *unrelated* register does **not** fix it -- only a `qft` call on the same register does) reproduces the true inverse-QFT matrix to ~1e-16. This held both for an `iqft` implemented via `with dagger: qft(qs)` and for a fully hand-written, dagger-free `iqft` with the swaps/rotations explicitly reversed and negated (rules out `dagger` specifically), and is independent of whether the driver is `@guppy` or `@guppy.comptime` (rules out comptime-calling-comptime as a separate cause -- an earlier version of this file wrongly claimed that as a distinct bug; it isn't, see below).

   Broader, non-deterministic symptom: a pytest file with `test_qft_matches_numpy_ifft` (sweeping `qft` alone over n=1..4) *and* `test_iqft_matches_numpy_fft` (sweeping `iqft` alone over n=1..4) produces failures whose exact pattern varies run to run -- one run failed only `qft[4]` and `iqft[2,3,4]`; a later run of the identical file failed `qft[1]` and `iqft[1,2,3,4]`. Critically, **the same `qft`-only sweep, in a file with no `iqft` at all, passed cleanly 3/3 times** run via actual pytest. So the corruption isn't simply "the same generic function monomorphized for multiple n" (an earlier version of this file claimed that as a *second*, separate bug -- it also isn't; a standalone script sweeping only `qft` over n=1,2,3,4 in one process was clean every time). It specifically requires `iqft` (or something about how it's compiled) to be present/exercised, and once triggered, the corruption isn't confined to `iqft`'s own results.

   We were unable to isolate a smaller repro (e.g. a single-qubit `rz`/`crz` case) or find the root cause in the time available. **Open item for whoever picks this up next**: try to reduce this to a minimal repro (ideally without depending on pytest specifically, to nail down whether pytest's import/collection machinery is actually relevant or just a red herring) and file it upstream against `guppylang`/`hugr`. Practical consequence for this package: `iqft`'s correctness is verified via round trips against `qft` (see `packages/qft/tests/test_correctness.py`), each test case run in its own subprocess (sidesteps the cross-contamination entirely, deterministic or not); a test documenting the isolated-failure case is kept and marked `xfail(strict=True)` rather than deleted.

6. **A plain Python function (or closure) cannot be called indirectly from inside a `@guppy` function body**, even if it just forwards to a real guppy definition: `guppy` resolves calls statically against known guppy globals, not arbitrary Python values. `def helper(q): real_guppy_func(q)` called as `helper(q)` inside a `@guppy` body raises `GuppyError` (`UnsupportedPythonValueError`). This ruled out a `_basis_state_matrix(n, op)`-style shared test helper; `qft`/`iqft` test drivers in this package are written out twice instead.

7. **Import statements are not allowed inside a `@guppy` function body** (only at module scope) -- raises `GuppyError` (`UnsupportedError`, "This statement").

8. `array`, `output`, `control`, `dagger`, `nat`, `owned`, `py`, `comptime`, etc. are all re-exported from `guppylang.std.builtins` (see `site-packages/guppylang/std/builtins.py`) -- no need to import from their "real" submodules (`guppylang.std.array`, `guppylang.std.lang`, `guppylang.std.num`, ...) directly.

9. `guppylang.std.num.int`/`nat` support `>>`, `&`, `//`, `%`, etc. -- real bitwise/integer ops are available in plain (non-comptime) guppy code, not just in `@guppy.comptime`. Used for basis-state preparation loops (`(k >> i) & 1`) in this package's tests without needing `comptime`.

10. `angle` (from `guppylang.std.angles`) is a frozen struct wrapping `halfturns: float`, *not* radians directly; `pi = angle(1)`. `float(some_angle) == some_angle.halfturns * pi`. Arithmetic like `pi / 2.0 ** k` works via `angle.__truediv__`.

11. `crz(control, target, angle)` -- control qubit first, target second (`Qubit ordering: [control, target]` per its docstring); matches the official QPE doc example.

12. **`with control(q0, q1): z(target)` -- a multi-controlled Z built from 2+ control qubits via the `control` modifier -- is broken in guppylang 1.0.2.** Found while building `packages/grover`. Confirmed with 2 controls (CCZ) and 3 controls (CCCZ): applying it to a uniform superposition produces a matrix that stays unitary but is measurably wrong (not the expected phase-flip-on-the-all-ones-state unitary) -- e.g. for 2 controls, `CCZ|+++>` should be `[0.3536]*7 + [-0.3536]` (real), but the actual result has spurious *imaginary* components on the two highest-index amplitudes instead: `[0.3536]*6 + [-0.3536j, 0.3536j]`. **`with control(q0, q1): x(target)` (multi-controlled X) is correct** -- it matches the built-in `toffoli` gate exactly, for both 2 and 3 controls. Workaround, the standard `H . (multi-controlled X) . H = multi-controlled Z` identity, confirmed exact (~1e-16) for 2 and 3 controls:
    ```python
    h(target)
    with control(*controls):
        x(target)
    h(target)
    ```
    `packages/grover/src/grover/grover.py` uses this throughout instead of a direct multi-controlled `z`. Not yet filed upstream; a minimal repro is in `packages/grover/tests/test_correctness.py::test_direct_multi_controlled_z_is_broken` (kept as `xfail(strict=True)`).

13. **The `control`/`dagger`/`power` `with`-modifiers are explicitly disallowed inside `@guppy.comptime` function bodies** -- calling them there raises `GuppyComptimeError` at runtime (their Python stub implementations in `guppylang/std/lang.py` just raise unconditionally; the real modifier logic only exists for the plain-`@guppy` AST path). This isn't documented anywhere we found -- discovered by trying it. Any function that needs `with control(...):` (e.g. a multi-controlled gate) must be a plain `@guppy` function, not `@guppy.comptime`, even if it's otherwise a good fit for comptime's generic-loop-unrolling style (like `packages/qft`'s `qft`/`iqft`).

14. **`with control(...)` accepts multiple qubits** (`with control(q0, q1, q2): x(target)`), confirmed via `guppylang_internals/cfg/builder.py` (`Control(e, e.args)`, no arity limit beyond "at least 1") and empirically. Not shown anywhere in the docs we found (the only documented example, in the canonical QPE page, uses a single control qubit) -- worth knowing this generalizes.

15. **Explicit generic-argument syntax at a call site, `func[arg1, arg2](...)`, works** for a plain `@guppy` function generic over `nat` parameters that don't appear in any argument's type (so can't be inferred) -- e.g. `oracle[marked](qs)` where `marked: nat` doesn't affect `qs`'s type `array[qubit, 3]`. This is not the same situation as `qft[n]`, where `n` **is** inferred from the array length and explicit instantiation is never needed. The generic argument expression itself must be a literal or a closed-over Python constant -- a live Python function call (`grover_search[marked, optimal_iterations(8, 1)]`) fails with `Error: Invalid type argument (Not a valid type argument)`, because guppy parses that subscript as guppy source to be resolved against guppy's own type system, not as a Python expression to evaluate first. Compute it in Python beforehand and pass the resulting int in via a closed-over variable instead.

16. **Explicit generic-argument syntax at a call site (`func[T](...)`, gotcha #15) does NOT work inside `@guppy.comptime`.** `qaoa_circuit[p](qs, gammas, betas)` inside a comptime body raises `GuppyComptimeError: Explicitly specifying type arguments of generic functions in a comptime context is not supported yet`. Found while building `packages/qaoa`. Workaround: rely on inference instead -- `qaoa_circuit(qs, gammas, betas)` (no `[p]`) works fine in comptime, with `p` inferred from `gammas`'/`betas`' array length, exactly as `qft(qs)` infers `n` from `qs`'s length.

17. **`array(... for x in some_list)` inside `@guppy.comptime` cannot infer the array's element type when `some_list` is empty** -- raises `GuppyComptimeError: Cannot infer the type of empty list`. Found while building `packages/qaoa`'s `run_qaoa` for the p=0 case (`gammas = betas = []`). Workaround: branch on the Python-level list in the comptime body (`if gammas: <build the array and use it> else: <handle the empty case directly, without constructing an empty guppy array>`) -- comptime traces real Python control flow, so this `if` is evaluated at trace time, not compiled as a guppy runtime branch.

18. **Comparing a *complex-valued* circuit's output against a hand-built reference needs full complex phase alignment, not just a +-1 sign flip.** `packages/qft` and `packages/grover`'s circuits are built entirely from real-valued gates (H, X, Z-type/CCZ-via-H-CCX-H), so any global-phase ambiguity in a test is a simple sign flip (`if vdot(actual, reference).real < 0: reference = -reference`, see grover's `_phase_aligned`). `packages/qaoa`'s `rz`/`rx` gates are genuinely complex, and using that same sign-only alignment against them fails with large, confusing diffs that look like a broken gate but aren't -- an isolated mixer-layer test showed a >0.9 max-abs-diff against a correct reference, entirely explained by a single non-trivial complex global phase the sign-flip check can't fix (it only ever multiplies by +-1). The general fix: rotate the reference by whatever unit complex phase best aligns it with the actual result, `reference *= vdot(reference, actual) / abs(vdot(reference, actual))`, not a conditional sign flip. See `packages/qaoa/tests/test_correctness.py`'s `_phase_align` and its module docstring for the full story, including the exact failing numbers before the fix.

19. **A raw `numpy.ndarray` closed over and iterated (`for p in params`) inside a *plain* `@guppy` function body is rejected, even though the same iteration over an actual Python `list` -- including one whose elements are `numpy.float64` -- works fine, in both plain and `@guppy.comptime` functions.** Found while building `packages/vqe_h2`: a test helper took `scipy.optimize.minimize`'s objective argument (always a numpy array) and passed it *directly* (no `list(...)` conversion) into a closure used by a plain `@guppy def main(): ... array(angle(p/pi) for p in params) ...`. That raised `GuppyError: Unsupported Python value ... Python value of type <class 'numpy.ndarray'>` -- rejecting the whole closed-over collection object, not a per-element type. We initially over-generalized this to "numpy.float64 elements are rejected" and nearly wrote that up as a broader bug (including a wrong claim that `packages/qaoa`'s `run_qaoa`/`optimize_qaoa` might have a latent version of it) -- **checked directly before committing that to this file, and it's wrong**: a real Python `list` containing `numpy.float64` elements (e.g. `list(some_ndarray)`) iterates and compiles fine via this exact `array(angle(p/pi) for p in params)` idiom, confirmed via both `.check()` and a full `.compile()` in both a plain `@guppy` function and (matching `packages/qaoa`'s own pattern) a `@guppy.comptime` one. So the actual, narrow, confirmed rule is: **convert a numpy array to a real Python `list` before closing over it for guppy iteration** (`list(x)` is sufficient; the individual element type doesn't need further coercion) -- don't pass a raw ndarray into the closure. `packages/qaoa`'s `run_qaoa`/`optimize_qaoa` already does this correctly (`list(x[:p])`/`list(x[p:])`). `packages/vqe_h2`'s `estimate_energy` additionally coerces each element with `float(p)` for defense-in-depth (harmless, and correct if it's ever called directly with something other than a plain list), but per the above, that specific coercion wasn't actually the load-bearing part of the fix -- converting to a `list` was. **Lesson for whoever adds the next package: verify a surprising error precisely (isolate collection-type vs element-type, plain vs comptime, etc.) before writing it up as a general bug** -- our first hypothesis here was more alarming and less accurate than the real, narrower issue.

20. **Closing over a Python `None` sentinel and comparing it against an `int` inside a `@guppy` body fails: guppy infers the closed-over value's *static* type from what it actually is, and `None` becomes `NoneType`, which has no `==` defined against `int`.** Found while building `packages/repetition_code`: a test parametrized `error_qubit` over `[None, 0, 1, 2]` (`None` = "no error injected"), closed over inside `if error_qubit == 0: x(qs[0])` etc. -- `GuppyTypeError: Operator not defined ... for None and int`, at `.check()` time (a real, would-hit-in-production error, not a test-only artifact -- any package closing over an `Optional[int]`-style sentinel hits this the same way). Fix: use a same-type sentinel instead of `None` -- this package's tests use `-1` for "no error" (all four packages before this one already happened to avoid `None`-typed sentinels, whether by luck or convention, so this hadn't come up yet).

## Testing methodology (read before adding a new package)

- **Non-Clifford circuits need `statevector_sim()` (Quest), not `stabilizer_sim()` (Stim).** Stim only simulates Clifford circuits exactly; QFT's controlled phase rotations `crz(..., pi/2**k)` for `k >= 2` are outside the Clifford group, so `packages/qft`/`grover`/`qaoa`/`vqe_h2` all use Quest throughout. `packages/repetition_code` is the first package in this registry where the circuit (`H`, `X`, `CX`, Z-measurement only) genuinely *is* Clifford-only, and it uses Stim as the primary backend accordingly -- confirmed by cross-checking both backends agree, not just assumed from "well, it's Clifford" reasoning (see its `test_stabilizer_sim_reproduces_statevector_sim_results`). Stim is both the *correct* and the faster choice there.
- **For a code/protocol whose defining property is "doesn't destroy quantum information" (error correction being the obvious case, but this generalizes to anything claiming non-destructiveness), test that property directly via the exact statevector on a genuine superposition input, not just "does it output the right classical bit" on a computational basis state.** `packages/repetition_code`'s `extract_syndrome` claims to extract the error syndrome *without collapsing the logical state* -- a test that only checked recovery starting from `|0>`/`|1>` inputs (property 1 in its README) could not actually distinguish a real syndrome-based implementation from a naive "always output the majority-vote bit" one that happens to get every computational-basis case right by coincidence. The real test (property 3): prepare a logical superposition (`H` before encoding), inject each error, run the full pipeline, and check the *exact* final statevector (`state_output`) reproduces the original superposition to ~1e-16 -- this is what actually distinguishes "a working error-correcting code" from "a lookup table that happens to match on classical inputs."
- **Reference implementation**: for QFT, the ground truth is `numpy.fft.ifft`/`fft` with `norm="ortho"` -- the unitary QFT matrix in the `qs[0]` = most-significant-qubit convention this package uses is *exactly* `numpy.fft.ifft(np.eye(2**n), norm="ortho")`, confirmed to ~1e-16 for n=1..4. Establish the qubit-ordering convention empirically first (see the `smoke_convention`-style check: apply `x` to a single qubit, run, and see which output index lights up) rather than assuming a convention from the source code alone.
- **Full-matrix testing over shot sampling**: rather than sampling measurement outcomes, this package's tests reconstruct the full 2^n x 2^n unitary by running every computational basis state through the circuit in one shot (`state_output` per basis state, `partial_states()` to read them back in order) and comparing the resulting matrix directly to the reference. This is exact (no statistical noise/tolerance needed beyond floating point), and also directly checks unitarity as a sanity property.
- **Isolate generic-parameter sweeps and independent circuits into separate subprocesses -- but only when the package's functions actually risk it.** See gotcha #5 above for why `packages/qft` needs this (`packages/qft/tests/_case_runner.py` + `subprocess.run` is the pattern). `packages/grover` doesn't use it: neither `oracle` nor `diffuser` is `@guppy.comptime` (can't be -- see gotcha #13), and we explicitly checked that sweeping `oracle`/`grover_search` over all 8 values of `marked`, and separately over 6 different `iterations` values, in one ordinary pytest process, produces no corruption (repeated runs, always clean). The bug's precondition (comptime + a dagger/derived-function relationship) genuinely doesn't apply here, not just "we didn't happen to hit it" -- see the grover section below. Don't reach for subprocess isolation reflexively; check whether the specific pattern that triggers gotcha #5 is actually present first.
- **Hand-verify at least one small case** in closed form in a test/comment (see `test_qft_hand_verified_n2` in `packages/qft/tests/test_correctness.py`, `test_oracle_flips_only_marked_amplitude` and the diffuser-fixes-`|s>`-exactly test in `packages/grover/tests/test_correctness.py`) so the automated reference formula itself has an independent sanity check.
- **Real-valued circuits (H, X, Z-type gates, no complex phases) still need phase-aligned comparisons against a hand-derived reference.** `packages/grover`'s full `grover_search` circuit's overall statevector sign, for a fixed iteration count, empirically varies with which item is marked (a physically meaningless global phase, not a bug -- see `packages/grover/tests/test_correctness.py`'s `_phase_aligned` and its module docstring). Compare `|amplitude|**2` directly where you can (no alignment needed, and it's what's actually observable), or align signs (flip the reference if `vdot(actual, reference).real < 0`) before comparing raw amplitudes.
- **Complex-valued circuits (any genuine `rz`/`rx`/`ry` rotation, not just real gates) need *general* phase alignment, not a sign flip.** See gotcha #18. `packages/qaoa`'s tests use `reference *= vdot(reference, actual) / abs(vdot(reference, actual))`.
- **Pin down a rotation-angle unit convention empirically against an exact reference, not by hand-derivation alone**, even when the math looks straightforward. `packages/qaoa`'s "gamma/beta in radians -> guppy `angle` in half-turns" conversion, and the exact sign/factor in the `cx; rz(-gamma); cx` cost-layer gadget, were both derived by hand first and then found subtly wrong against `scipy.linalg.expm` on the first attempt (an easy-to-make factor-of-2 or off-by-a-sign error) -- always cross-check the final circuit against an independent, exact classical computation (matrix exponential, or a small hand-computed case) before trusting the hand derivation, the same way `packages/qft` empirically pinned down its qubit-ordering convention rather than assuming one.

## Grover package notes (guppylang 1.0.2, added 2026-08-29)

- No official Grover example was found in Quantinuum's docs (checked `docs.quantinuum.com/guppy` and web search) -- the multi-qubit `control` modifier's behavior (gotchas #12-14 above) was reverse-engineered from `guppylang_internals/cfg/builder.py` and confirmed empirically, not documented anywhere we found. If Quantinuum publishes a Grover/oracle example later, cross-check this package against it.
- **Checked all three of `packages/qft`'s documented bug patterns against this package, as follow-up work explicitly asked us to. None apply, and we verified each rather than assuming:**
  - Gotcha #5 (iqft-isolation / cross-contamination) requires a `@guppy.comptime` function used *only* via composition with another comptime-generic function derived from it (dagger or hand-reversed). Grover has no such relationship -- `oracle` and `diffuser` are independent, non-comptime, non-dagger functions (comptime is actually *unavailable* here, see gotcha #13) -- and we confirmed no corruption sweeping `marked` (8 values) or `iterations` (6 values) in-process.
  - The "comptime calling comptime" framing (folded into gotcha #5 after we found it was a mis-attribution) doesn't apply either, for the same reason: nothing here is `@guppy.comptime`.
  - No multi-`n` monomorphization sweep applies -- this package fixes the register size at 3 qubits (see "What's here" in `packages/grover/README.md` for why full `n`-generality isn't offered).
- **What Grover *did* find**: a new, unrelated bug -- `with control(q0, q1): z(target)` is broken (gotcha #12). Not a QFT-pattern regression; a different corner of the same `control`/modifier machinery (multi-qubit `with control(...)`, gotcha #14, is itself new-to-this-package territory -- `packages/qft` only ever used single-qubit `with control(...)` indirectly via `with dagger:`, and never used `control` directly at all).

## QAOA package notes (guppylang 1.0.2, added 2026-08-29)

- No official QAOA/MaxCut example was found in Quantinuum's docs (checked `docs.quantinuum.com/guppy` and web search), same as grover -- the entrypoint measurement/output pipeline (`measure_array` + `collect_measurements` + `output(tag, array[bool, n])` + `EmulatorResult.register_bitstrings()`), the `array(... for x in python_list)` comptime construction pattern, and the exact `angle`-unit convention for `rz`/`rx` were all pinned down from installed source + empirical verification against `scipy.linalg.expm`, not from docs.
- **Checked CLAUDE.md's full bug list against this package's needs (parameterized rotation gates + a classical optimization loop), as explicitly requested by the task brief. Verified rather than assumed clean:**
  - Gotcha #5 (iqft-isolation / cross-contamination): doesn't apply. Its precondition is a comptime function used *only* via composition with another comptime function *derived from it* (dagger or hand-reversal) -- `cost_hamiltonian_layer`, `mixer_layer`, and `qaoa_circuit` are independent circuit-builders with no such parent/derived relationship. Confirmed directly (not just argued): ran the full `cost_hamiltonian_layer` -> `mixer_layer` -> `qaoa_circuit` chain, called from a comptime `main()`, for p = 1, 2, and 3 layers and 5 different (gammas, betas) sets, all sequentially in one process, against an exact `scipy.linalg.expm` reference -- ~1e-16 agreement every time (see `tests/test_correctness.py::test_full_circuit_matches_exact_reference`). No subprocess isolation needed, matching `packages/grover`'s finding (not `packages/qft`'s).
  - Gotcha #12 (`with control(...): z(...)` broken): doesn't apply -- QAOA needs no multi-controlled gates at all (only single-qubit `rz`/`rx` and `cx`), so `control` is never used here.
  - Gotcha #13 (`control`/`dagger`/`power` forbidden in `@guppy.comptime`): doesn't block anything, since QAOA never needs those modifiers -- but it's part of *why* QAOA safely leans on comptime as heavily as it does (three levels of comptime-calling-comptime: `main` -> `qaoa_circuit` -> `cost_hamiltonian_layer`/`mixer_layer`), unlike `packages/grover`, which was forced into plain `@guppy` functions specifically because it needed `control`.
- **What QAOA *did* find**: gotchas #16, #17, and #18 above -- explicit generic subscripting forbidden in comptime (distinct from gotcha #15, where it works fine in *plain* guppy), empty-Python-list array construction forbidden in comptime, and the general-complex-phase-alignment testing lesson (a real methodology gap this package's initial tests hit, not a guppylang defect). None of these are upstream bugs in the sense gotchas #5/#12 are -- #16/#17 are compiler limitations with clear, documented workarounds, and #18 is purely about how *we* write tests.
- Confirmed empirically (not assumed from the QFT/Grover precedent) that Selene's Stim backend rejects this package's circuits outright: `.stabilizer_sim()` raises `EmulatorError` with Selene's own message, `RZ(...) is not representable in stabiliser form. Theta must be an (approximate) multiple of pi/2 for Clifford operations.` -- see `test_stabilizer_sim_rejects_generic_angles`.

## VQE-H2 package notes (guppylang 1.0.2, added 2026-08-29)

VQE/chemistry is Quantinuum's own flagship application area (InQuanto), so this package's rigor bar was set higher than qft/grover/qaoa's -- every numeric claim is checked against an independent, from-scratch numpy reference, not just the guppy code's own internal consistency. See `packages/vqe_h2/README.md`'s "How correctness was verified" section for the six-part methodology.

- **The Hamiltonian is cited, not derived.** Per the task brief, we did not hand-derive an H2 qubit Hamiltonian. Used PennyLane's official ["A brief overview of VQE" demo](https://pennylane.ai/demos/tutorial_vqe/) (Xanadu), which explicitly confirms Jordan-Wigner mapping in its own text -- a 4-qubit, 15-term, STO-3G Hamiltonian, quoted verbatim (full float64 precision) in `vqe_h2.py`. **Independently re-verified before trusting it** (also per the task brief, and standard practice before relying on a secondary source for a numeric table): exact diagonalization (`numpy.linalg.eigvalsh` on the 16x16 matrix, built from Pauli matrices + `np.kron`) gives -1.13726332 Hartree, matching the ~-1.137 Hartree value widely quoted in the VQE literature, and close to (not identical to -- consistent with their optimizer not running to full convergence) the -1.13726250 Hartree the PennyLane tutorial itself reports reaching. A backup source was also checked and explicitly rejected: O'Malley et al. 2016 (arXiv:1512.06860)'s well-known 2-qubit H2 Hamiltonian is **Bravyi-Kitaev, not Jordan-Wigner** (confirmed via the paper's own text) -- don't cite it as a JW Hamiltonian despite it being the most commonly-reproduced "2-qubit H2 Hamiltonian" in tutorials.
- **The ansatz's exactness was verified numerically *before* writing any guppy code**, not assumed: a pure-numpy calibration script (Pauli matrices, `RY`/`CNOT` matrices, `scipy.optimize`) checked whether a simple hardware-efficient ansatz (Hartree-Fock reference + one RY-per-qubit layer + a CNOT ladder, 4 parameters) could reach the true ground state at all, before committing to it as the shipped `ansatz_circuit`. It can -- confirmed reaching -1.137263 Hartree from multiple random restarts on the exact objective.
- **Checked CLAUDE.md's full bug/finding list against this package's needs (parameterized ansatz + classical optimization loop, like QAOA), as explicitly requested by the task brief:**
  - Gotcha #5 (iqft-isolation): doesn't apply -- no dagger/derived-function relationship anywhere in this package.
  - Gotcha #12 (`with control(...): z(...)` broken): doesn't apply -- no multi-controlled gates needed (`ansatz_circuit` uses only `X`, `RY`, `CX`).
  - Gotcha #13 (`control`/`dagger`/`power` forbidden in comptime): doesn't block anything -- `ansatz_circuit` itself is a **plain** `@guppy` function (not comptime at all -- it only needs `range(N_QUBITS)`-style loops, no iteration over a Python data structure), unlike `qaoa`'s layer functions. Only the *measurement*-circuit builder (`_build_measurement_circuit`, which iterates a Python `{qubit: Pauli}` dict to decide per-qubit basis rotations, the same reason `qaoa`'s `cost_hamiltonian_layer` needs comptime for its edge list) uses `@guppy.comptime`.
  - Gotchas #16/#17 (explicit generic subscripting / empty-list array construction forbidden in comptime): not hit -- this package never needs explicit generic instantiation (no `nat`-generic functions at all -- `N_QUBITS` is a fixed Python constant, not a guppy generic), and never constructs an empty array.
  - Gotcha #18 (complex-valued circuits need general phase alignment): applies to nothing here directly -- `ansatz_circuit` is real-valued (X, RY, CX only, matching qft/grover's situation, not qaoa's), so exact-statevector tests use a plain +-1 sign flip. It's the *measurement*-circuit builder's basis-rotation gates (`h`, `sdg`) that are complex, but those are only ever used in the real, shot-sampled `estimate_energy` pipeline, which is tested for numeric agreement (not exact statevector equality), so phase alignment doesn't come up there either.
- **What VQE-H2 *did* find**: gotcha #19 above (a raw `numpy.ndarray`, as opposed to a real Python `list`, closed over and iterated inside a guppy body is rejected) -- and, as importantly, a case where our *first hypothesis* about that bug was wrong and over-generalized (nearly leading us to falsely flag a latent bug in `packages/qaoa`) until we checked it directly. Also independently verified the `h`/`sdg` Pauli-basis-rotation identities (X-basis: `h(q)` before Z-measurement; Y-basis: `sdg(q); h(q)`) against known eigenstates before using them in `estimate_energy` -- these aren't new to guppy (standard VQE/measurement technique) but were confirmed empirically here rather than assumed correct from memory, consistent with this package's higher rigor bar.
- **Confirmed (not assumed) that Quest, not Stim, is required**, same reasoning as qaoa: `ansatz_circuit`'s `RY` gates take continuous, non-Clifford-in-general angles.
- **The optimization landscape has many local minima** -- see `vqe_h2.py`'s `DEFAULT_X0` and `packages/vqe_h2/README.md`. Worth knowing for any *future* variational package (this pattern will very likely recur for VQE-style problems in general, not just H2): don't assume an "obvious" starting point (all-zero parameters, small perturbations of it) will let a modest-budget classical optimizer find the true minimum -- check directly against the exact, noiseless objective first, the same way `packages/qft` empirically checked its qubit-ordering convention rather than assuming one.
- **This package's tests are, by a wide margin, the highest-subprocess-spawn-volume in this registry** (`estimate_energy` alone is 5 real circuit runs, not 1, and it's called once per classical-optimizer objective evaluation). During development, on this dev machine, the two heaviest tests hit CLAUDE.md gotcha #3's transient-block issue *persistently* -- failing consistently across several full re-runs and multiple rounds of trimming the optimizer budget down, not the usual "fails once, passes on retry" pattern the earlier packages saw. See those two tests' docstrings in `packages/vqe_h2/tests/test_correctness.py` for the specifics. If you're extending this package (or writing the next variational one) and hit sustained `WinError 4551` failures even after retries, that's very likely this same environmental condition, not a new regression -- checked by confirming the other, lower-volume tests (which independently verify the Hamiltonian, the ansatz circuit, and the measurement pipeline against exact numpy references) pass reliably throughout.

## repetition_code package notes (guppylang 1.0.2, added 2026-08-30)

This is the final package in this registry's initial planned set (see "Planned next packages" below) -- QEC rather than an algorithm subroutine, and the first package to lean heavily on mid-circuit measurement and measurement-driven classical control flow (`extract_syndrome` measures ancillas partway through the circuit, not at the very end; `correct` branches on those measured bits), which no earlier package exercised at all.

- No official guppy repetition-code walkthrough was found in Quantinuum's own docs, but a genuinely useful pointer turned up: the [Guppy Playpond](https://play.guppylang.org/) browser playground advertises a ready-made "quantum error correction repetition code" example among its samples (alongside a Bell state, repeat-until-success, and adaptive QPE) -- we couldn't extract its source via `WebFetch` (the page is a live editor, not static content), so it wasn't used as a reference, but it's worth opening directly (in a browser) before extending this package, as a second data point against what we built independently here. Also found and used: `guppylang.std.quantum.project_z(q: qubit) -> Measurement`, a genuine *non-destructive* Z-basis measurement (unlike `measure`, which takes `q: qubit @ owned` and consumes it) -- implemented internally via destructive-measure-then-reprepare-a-fresh-qubit, conditionally flipped back to match the outcome. Not needed for this package (ancillas are meant to be destructively measured and discarded -- there's nothing to preserve), but relevant for any future package that needs to measure a *data* qubit mid-circuit and keep using the same qubit afterward. Also found platform-specific `measure_and_reset` in `guppylang.std.qsystem.{helios,sol}` for physical-ancilla-reuse scenarios -- not used here either, for the same reason (no reuse needed with only 2 ancillas and no code-distance/repeated-round structure).
- **Checked CLAUDE.md's full bug/finding list against this package's needs (ancilla-based syndrome extraction, classically-controlled correction), as explicitly requested by the task brief -- this was the most important check in this package's development, since mid-circuit measurement + classical control flow is genuinely new territory here:**
  - Gotcha #5 (iqft-isolation): doesn't apply -- no dagger, no derived-function relationship, no comptime at all in this package.
  - Gotcha #12 (`with control(...): z(...)` broken): doesn't apply, and *can't* come up by construction -- `correct`'s qubit selection is entirely classical (`if` on two measured `bool`s), never quantum `with control(...)`. This is exactly the "classically-controlled correction" the task brief called out, and it's a genuinely different mechanism from every earlier package's quantum-controlled gates.
  - Gotchas #13/#16/#17 (comptime-only restrictions): don't apply -- `encode`/`extract_syndrome`/`correct` are all plain `@guppy` functions. This package needs no `@guppy.comptime` at all: there's no Python-level data structure to iterate (no edge list, no Pauli-term dict) -- the 3-qubit syndrome table is small and fixed, expressed directly as three `if` statements.
  - Gotcha #18 (phase alignment for complex circuits): doesn't apply -- every gate here is real-valued (H, X, CX; no rz/rx/ry anywhere), so exact-statevector tests use the simple qft/grover-style +-1 sign flip, not qaoa's general complex alignment.
  - Gotcha #19 (raw ndarray rejected in a guppy closure): doesn't apply -- this package has no classical optimizer, so nothing ever hands a numpy array to a guppy-touching function.
- **What repetition_code *did* find**: gotcha #20 above (closing over a Python `None` sentinel and comparing it to `int` inside a guppy body fails; guppy statically types the closed-over `None` as `NoneType`) -- a real, would-hit-in-production finding, not a test-only quirk, since any package closing over an `Optional[int]`-style value hits the same thing. Otherwise: **mid-circuit measurement and measurement-driven classical control flow both worked exactly as documented on the first attempt** -- `extract_syndrome`'s ancilla-based, non-destructive syndrome extraction (verified via the exact-statevector superposition test, not just classical-bit recovery) and `correct`'s classical feedforward needed no workarounds at all. Checked carefully rather than assumed clean, per the task brief, and it turned out to genuinely be clean -- worth recording explicitly, since every other package in this registry found *something*, and a false "we didn't find anything" from not having looked hard enough would be worse than finding nothing after actually looking.
- Confirmed empirically (not assumed from "well, it's Clifford" reasoning) that `stabilizer_sim()` (Stim) is not just usable but produces results identical to `statevector_sim()` (Quest) for this circuit -- see `test_stabilizer_sim_reproduces_statevector_sim_results`. The first package in this registry where Stim is the *primary* test backend rather than Quest.
